# Design

## Context

Проект стартует с нуля (см. proposal.md — Why). Выбранный стек: мобильный клиент на React Native + Expo, backend на Go + PostgreSQL. Единственная целевая среда деплоя на старте — один VPS: 1 vCPU, 957Mi RAM (без swap), 9.6GB SSD, Ubuntu 22.04, без Docker. Это жёстко ограничивает архитектуру: нельзя рассчитывать на несколько тяжёлых процессов (отдельный Redis, очереди, кэш-слои) без явного учёта памяти.

## Goals / Non-Goals

**Goals:**
- Единый Go-бинарник (backend-монолит) с минимальным набором процессов на сервере: сам backend + PostgreSQL
- Архитектура, которая работает в 1GB RAM без OOM, с понятным путём масштабирования (переезд на БД/сервер побольше), когда нагрузка вырастет
- Реалтайм-чат без отдельного message broker — через WebSocket-хаб внутри самого Go-процесса

**Non-Goals:**
- Горизонтальное масштабирование backend (несколько инстансов, балансировка) — не нужно на MVP-нагрузке и не поместится в текущий сервер
- Полноценная admin-панель модерации — в этом change только автоматический порог жалоб и сбор жалоб (см. moderation spec)
- Хранение/обработка медиа на самом VPS — диска и памяти под это недостаточно

## Decisions

### Backend как единый Go-бинарник (монолит), без Docker на старте
Один процесс proще в эксплуатации на 1GB RAM: нет накладных расходов контейнеризации (Docker-демон сам по себе съедает заметную часть и так небольшой памяти). Бинарник запускается как systemd-сервис. Docker откладываем до момента, когда появится второй сервер или нужда в изоляции — тогда миграция на Docker/Compose делается отдельным change.
Альтернатива (отклонена): Docker Compose с самого начала — даёт переносимость, но съедает лишние ~100-200MB RAM на demon и слои, что критично при 957Mi total.

### PostgreSQL + PostGIS локально на том же сервере, с жёсткими лимитами памяти
PostGIS даёт готовые geo-индексы (GiST) для запроса "кандидаты в радиусе N км" без написания собственной геоиндексации. PostgreSQL конфигурируется с урезанными `shared_buffers` (~128-192MB), `work_mem`, `max_connections` (точка отказа при 1GB RAM — слишком много соединений). Backend держит небольшой пул соединений (например, 5-10).
Альтернатива (отклонена на старте): managed БД в облаке (Neon/Supabase free tier) — разгрузила бы память сервера, но пользователь явно выбрал Postgres локально с лимитами как стартовый вариант; managed БД остаётся опцией для миграции, если локальная не выдержит.

### Обязательный swap-файл перед деплоем
На сервере сейчас swap отсутствует (подтверждено `free -h`). Без swap любой кратковременный всплеск (например, сборка индекса, конкурентные запросы) рискует словить OOM-killer и уронить процесс. Решение: создать swap-файл (1-2GB) как первый шаг инфраструктурных задач, до разворачивания backend и БД.

### Реалтайм-чат через WebSocket-хаб в самом Go-процессе
Отдельный брокер сообщений (Redis Pub/Sub, RabbitMQ и т.п.) добавил бы ещё один процесс и расход памяти, не оправданный на MVP-масштабе (один backend-инстанс, умеренное число одновременных соединений). WebSocket-соединения и рассылка между участниками мэтча управляются in-memory хабом внутри самого backend-процесса; персистентность сообщений — в PostgreSQL.
Риск при будущем масштабировании на несколько инстансов backend учтён в разделе "Риски / Trade-offs".

### Фото профиля — во внешнем объектном хранилище (S3-совместимом), не на диске VPS
10GB SSD и 1GB RAM не рассчитаны на хранение и тем более обработку (ресайз, компрессия) медиаконтента при росте числа пользователей. Backend принимает фото через presigned URL на загрузку напрямую в объектное хранилище (например, Cloudflare R2, Backblaze B2 или аналог с free/дешёвым тарифом), сохраняя в БД только ссылки/ключи.

### Тёмная тема по умолчанию в мобильном клиенте
Приложение запускается с тёмной темой как единственной/основной темой оформления на MVP (без переключателя светлая/тёмная на старте). Решение продуктовое: тёмная тема соответствует вечернему/ночному сценарию использования приложения. Реализуется через тему React Native (например, React Navigation theming + стили компонентов), без зависимости от системной темы устройства.

### Push-уведомления через Expo Push Notification Service
Так как клиент на Expo, Expo Push Service избавляет от прямой интеграции с APNs/FCM на старте (единый HTTP API для push на оба платформы). Backend хранит Expo push-токен устройства и отправляет уведомления через Expo Push API.

### Объектное хранилище для фото: Cloudflare R2
Выбран Cloudflare R2 — бесплатный тариф покрывает MVP-объёмы (10GB хранения, без платы за исходящий трафик, что особенно важно при показе фото в ленте). S3-совместимый API позволяет использовать стандартные SDK/клиенты. Интеграция — через presigned URL на загрузку, как описано выше.

### Аутентификация: Telegram Login + email/пароль, без SMS на MVP
SMS-подтверждение по номеру телефона отложено на стадию после MVP — это убирает платную внешнюю зависимость (SMS-провайдер) и открытый вопрос выбора провайдера на старте проекта. Вместо этого на MVP два независимых способа входа:
- **Telegram Login Widget** — бесплатно, даёт реальное подтверждение личности через существующий Telegram-аккаунт пользователя (криптографическая подпись данных от Telegram проверяется backend'ом), подходит для русскоязычной аудитории, где Telegram распространён
- **Email + пароль** — классический способ без внешних зависимостей, резервный вариант для пользователей без Telegram

Оба способа выдают одинаковые JWT access/refresh токены (см. ниже), работают независимо друг от друга; у пользователя может быть привязан один или оба способа входа. Отдельный пользователь в БД идентифицируется внутренним user ID, а не способом входа.

### JWT access/refresh токены для сессии
Access-токен — короткоживущий JWT, refresh-токен — долгоживущий, хранится хэшированным в БД с возможностью отзыва (logout, moderation-блокировка). Не зависит от способа входа (Telegram или email/пароль).

## Risks / Trade-offs

- [1GB RAM — любой непредвиденный всплеск памяти роняет сервер] → Swap-файл как обязательный первый шаг деплоя; мониторинг `free`/OOM-логов; с самого начала держать пул БД-соединений маленьким и урезанные настройки PostgreSQL
- [WebSocket-хаб в памяти одного процесса не переживёт перезапуск backend и не масштабируется на несколько инстансов] → Приемлемо для MVP с одним инстансом; при будущем масштабировании — выделение realtime-слоя с внешним pub/sub как отдельный change
- [Объектное хранилище (Cloudflare R2) — внешняя зависимость] → Бесплатный тариф покрывает MVP-нагрузку; presigned-URL подход не создаёт точки отказа в самом backend
- [Без SMS-подтверждения телефона пользователи Telegram/email менее верифицированы, чем по номеру] → Приемлемо для MVP; верификация по телефону — отдельный change после MVP, когда появится SMS-провайдер
- [Отсутствие admin-панели модерации] → Автоматический порог жалоб (moderation spec) покрывает худшие случаи на MVP; ручная панель — следующий change после проверки продукта

## Migration Plan

Так как это greenfield-деплой (на сервере пока ничего не развёрнуто), это не миграция существующей системы, а первичное разворачивание:
1. Создать swap-файл на сервере (до установки PostgreSQL/backend)
2. Установить и сконфигурировать PostgreSQL + расширение PostGIS с урезанными параметрами памяти
3. Прогнать миграции схемы БД
4. Собрать и задеплоить Go-бинарник backend как systemd-сервис
5. Настроить reverse proxy (nginx) перед backend по HTTP; TLS (Let's Encrypt/certbot) отложен до появления домена (Let's Encrypt не выдаёт сертификат на голый IP) — добавляется отдельным change
6. Прогнать health-check и smoke-тест ключевых эндпоинтов (auth, profile, feed, match, chat, moderation, notifications)

Откат (rollback): если задеплоенная версия backend нестабильна — остановить systemd-сервис, вернуть предыдущий бинарник (хранить N последних сборок на диске) и перезапустить; миграции схемы БД пишутся обратимыми (down-миграции) на случай отката схемы.
